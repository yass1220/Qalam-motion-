Une tâche à la fois, une PR par objectif

Cette PR ajoute un fichier AGENTS.md à la racine du dépôt. Il rend explicites les règles de périmètre, de commit et de publication attendues pour toutes les interventions.

1. Le contexte

Les bases : branche, commit et pull request

Un commit enregistre un ensemble de changements. Une branche regroupe des commits autour d'un travail. Une pull request propose d'intégrer cette branche dans une cible : elle donne aux autres contributeurs un endroit pour relire le diff et voir les contrôles avant la fusion.

Lorsque plusieurs sujets indépendants entrent dans une même PR, le titre ne décrit plus précisément le contenu. La revue devient plus difficile : un correctif peut être prêt tandis qu'une autre modification nécessite encore une décision. Le retour arrière devient lui aussi moins précis.

Le dépôt possède déjà une CI qui exécute lint, typage, tests et build. Il ne contient pas encore de fichier de contribution AGENTS.md à sa racine. Cette PR ajoute des consignes communes au projet sans modifier l'application ou la configuration GitHub.

Le problème à résoudre est concret : découvrir un autre défaut pendant un correctif ne doit pas conduire à le corriger dans la même branche. Annoncer cet élargissement ne suffit pas à l'autoriser.

2. L'intuition

Le périmètre est un contrat de revue. Il décrit le résultat attendu et les changements nécessaires pour l'obtenir. Tant que ce contrat ne change pas, une autre découverte reste une information à signaler.

Définir

Un objectif, ses critères et une branche depuis la bonne base.

Vérifier

Seulement les changements utiles, puis les contrôles adaptés.

Livrer

Une PR dédiée, ses preuves et ses limites. Fusion sur demande explicite.

Exemple. Pendant le correctif du sélecteur de langue, une erreur de tarif est découverte. Elle doit être signalée pour arbitrage et suivi distinct. Elle ne devient pas automatiquement une partie du correctif du sélecteur.

Une tâche peut toucher plusieurs fichiers : composant, CSS, catalogue et tests peuvent tous servir le même résultat. La règle sépare les objectifs, pas les extensions de fichiers ou le nombre de commits.

3. Ce que le fichier impose

Périmètre et séquence

La première section exige un seul objectif à la fois, interdit les corrections opportunistes et décrit quoi faire si un prérequis indépendant bloque le travail. Un changement de priorité doit être clarifié : terminer ou mettre explicitement en pause avant de passer à une autre tâche. Le travail existant doit être préservé.

Une nouvelle tâche autorisée utilise une nouvelle branche. Les retours de revue restent dans la PR tant qu'ils servent son objectif. Une PR ouverte n'autorise pas à commencer spontanément une autre issue.

Branches et commits

Les branches temporaires portent des noms neutres tels que fix/header-layout ou docs/project-rules. Les changements d'une autre tâche ne doivent jamais être écrasés ou embarqués.

fix: stabilize header layout
feat: add locale switch
docs: clarify contribution rules

Les commits et titres de PR suivent Conventional Commits, avec une description franglish de cinq mots maximum après le préfixe. L'auteur humain configuré reste l'auteur. Le fichier interdit les secrets, crédits de génération, contournements de hooks et réécritures non autorisées.

Publication et fusion

Demande de commit

Enregistrer le travail local. Le push n'est pas implicite.

Demande de PR

Pousser la branche de travail et ouvrir la PR. La fusion n'est pas implicite.

Demande de fusion

Vérifier cible, dernier commit, contrôles et revues requis avant de fusionner.

Les pushs directs vers main et dev sont interdits, y compris pour la documentation, une urgence ou un merge local. Les intégrations passent par une PR ; une release de dev vers main suit aussi cette règle.

Après fusion, seules les branches temporaires sans commit unique peuvent être nettoyées. Le texte exclut explicitement main, dev et toute branche partagée encore utilisée : une release ne doit jamais entraîner la suppression de dev.

Qualité et compte rendu

Les sections finales imposent pnpm, TypeScript strict, la réutilisation de l'existant et des vérifications proportionnées. Une modification documentaire demande une relecture et une vérification des liens et de la structure ; les changements de pages ou de routage nécessitent aussi build et tests HTTP. Les validations humaines et les actions de production restent explicites.

Chaque nouvelle PR reçoit une explication HTML versionnée dans docs/reviews/, avec contexte, intuition, parcours des changements et cinq questions. Ce document explique le même objectif ; il n'introduit pas un second correctif.

4. Validation et limites

VérificationRésultat
Typagepnpm exec tsc --noEmit a réussi avant le commit des règles.
Diffgit diff --cached --check a réussi.
RelecturePérimètre, autorisations et exception de nettoyage des branches permanentes vérifiés.
ApplicationAucun fichier applicatif modifié, aucun serveur lancé.
Consignes et protections sont complémentaires. AGENTS.md est lu par les outils compatibles et fournit une règle de contribution. Il ne bloque pas techniquement un push et ne remplace pas les protections de branches, les droits d'accès ou les contrôles CI de GitHub. Ces réglages ne sont pas modifiés dans cette PR.

Cette PR est proposée pour revue vers dev. Sa création ne constitue pas une autorisation de fusion.
