Un socle Next.js propre pour Qalam Motion

Cette pull request #20 fournit la base du nouveau site. Elle remplace l’arborescence de développement Express par une application Next.js à la racine. Elle ne porte pas encore les fonctions commerciales.

ContexteIntuitionCodeQuiz

1. Contexte

Comprendre les briques, depuis le début

Un navigateur demande une URL à un serveur et reçoit du HTML. Le HTML décrit le contenu ; le CSS règle la présentation. JavaScript apporte ensuite les interactions nécessaires. Une page n’a donc pas besoin d’être fabriquée entièrement dans le navigateur pour être interactive.

Next.js organise une application React par routes. Avec l’App Router, app/page.tsx correspond à l’accueil et app/layout.tsx porte la structure commune. Les fichiers TSX sont du TypeScript contenant le balisage des composants. Le mode strict vérifie les types, mais ne valide pas à lui seul les données reçues par une API : cette validation viendra avec les parcours métier.

Une page prégénérée est produite au build, avant les visites. Le serveur peut servir ce résultat sans recalculer son contenu pour chaque visiteur. Ce modèle convient à la préversion actuelle ; il ne suffit pas pour sécuriser une administration ou capturer un paiement, qui exigent des traitements à la requête.

La situation avant ce changement

Le dépôt contenait un serveur Express et des pages HTML arabes. La page d’accueil possédait déjà un contenu HTML substantiel. Les modules côté serveur géraient demandes gratuites, commandes, paiement PayPal, stockage PostgreSQL ou JSON et notifications persistantes. Une suite de 19 scénarios couvrait une partie importante de ces contrats. Le système n’était donc pas une simple page vide à remplacer.

Samy a validé un nouveau départ dans l’arborescence : uniquement le site Next.js en construction, avec le cahier des charges dans docs/. Le code de référence reste accessible à 981706e.

Limite essentielle : retirer Express de cette branche ne migre ni les commandes ni les paiements. Cette préversion n’est pas prête à remplacer le service actif et aucun déploiement n’est inclus.

2. Intuition

On commence par une base facile à retrouver et à vérifier, puis on porte chaque capacité dans un lot explicite. Ajouter une structure monorepo ou un dossier src/ n’apporterait ici aucune valeur demandée : la convention retenue place l’application directement à la racine.

Référence historique

Express + HTML arabe + contrats métier.
Exemple : formule short, 15 USD calculés côté serveur.

Cette PR

Next.js + TypeScript strict + Tailwind.
Exemple : GET / reçoit une page anglaise prégénérée.

Lots suivants

i18n, données, auth, métier et tests.
Exemple : /ar reste arabe même si le navigateur est anglais.

La séparation est fonctionnelle, pas une autorisation d’oublier l’ancien comportement. Lors du portage d’un paiement de 15 USD, le navigateur ne doit toujours pas pouvoir imposer 1 USD : les prix serveur, références, montants, devises, unicité des captures et écritures atomiques devront être repris et testés.

À ce stade, seul l’exemple GET / est implémenté. La page est marquée noindex pour cette préversion, et le build l’identifie comme statique. Cela ne démontre pas encore le rendu de futures pages localisées ou l’isolation de données privées qui n’existent pas dans ce socle.

3. Parcours du code

Une seule application à la racine

FichierResponsabilité

app/page.tsxAccueil de développement ; aucun formulaire ou paiement.

.postcssrc.jsonConfiguration déclarative du plugin Tailwind, sans configuration JavaScript.
package.json, pnpm-lock.yamlDépendances Next/React et outils, versions verrouillées ; anciennes dépendances Express retirées.
docs/CAHIER-DES-CHARGES.mdExigences et décisions de structure/langue servant de guide aux prochaines issues.

Les commandes suivent cette structure

pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm build
pnpm dev --port 3155

Il n’y a plus de commande indirecte dev:web. Le port 3155 correspond au sandbox local de cette tâche ; les autres environnements doivent employer leur propre port. Le runtime demandé est Node.js 22.13 minimum et le gestionnaire déclaré est pnpm 10.28.2.

La CI vérifie le socle livré

Le workflow exécute installation figée, lint, typecheck strict et build. Il se déclenche sur les branches principales, les branches feat/** et les pull requests vers main/dev. Les validations locales sont réussies ; la première exécution GitHub de la base e4b1ce2 est également verte.

La suite Express n’est pas exécutée par cette CI. Cette différence est explicite dans #8, clôturée sur le périmètre du socle. Le portage des scénarios accompagne les domaines et reste suivi dans #18.

Ce qui reste volontairement ouvert

  • #9 : en/ar/fr/es, anglais de base/fallback, détection initiale et choix explicites conservés.
  • #13 : validation runtime, demandes et paiements avec leurs garanties.
  • #15 : pages finales et composants utiles selon le contenu approuvé.
  • #18 : tests métier portés, intégration, navigateur et contrôles de recette.

La configuration Railway historique est retirée de cette branche avec l’ancien service. Il faudra préparer et approuver explicitement la topologie du nouveau site, les migrations et la bascule. Cette PR ne prouve ni restauration de production ni bon fonctionnement des futurs paiements.
