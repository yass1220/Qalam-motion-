Une langue explicite dans chaque URL

La PR #21 donne quatre versions à l’accueil de préversion et établit le routage pour les pages à venir. La base reste Next.js à la racine, sans src/ ou apps/web/, avec TypeScript strict.

1. Contexte

Les bases : langue du navigateur, URL et rendu serveur

Le navigateur peut indiquer ses langues préférées dans l’en-tête Accept-Language. Il peut transmettre plusieurs langues, parfois avec une région et un poids : ar-MA,fr;q=0.8 exprime ici une préférence arabe avant le français. Ce signal n’est pas une géolocalisation et ne garantit pas de connaître la langue de tous les réglages du téléphone.

Une URL comme /ar identifie directement une version arabe. Elle reste valable lorsqu’un lien est partagé à une personne dont le navigateur est français. Le cookie NEXT_LOCALE joue un autre rôle : mémoriser une préférence pour la prochaine visite d’une URL sans préfixe. Il ne doit pas forcer le visiteur à quitter une URL explicitement choisie.

Enfin, le HTML peut être préparé au build. Une version prégénérée ne doit pas lire la session ou les préférences à chaque rendu. Le proxy négocie l’entrée, puis la route localisée fournit son contenu stable. Les pages privées et les futurs paiements suivront leurs propres contrats dynamiques.

Avant cette PR, le socle contenait une seule page anglaise dans app/page.tsx et un layout fixant lang=en et dir=ltr. Aucun catalogue de messages ni proxy de langue n’était présent. Le cahier des charges exige quatre langues, le RTL arabe et des URL explicites conservées.

Périmètre : il existe toujours un seul type de page informative, l’accueil de préversion. Les quatre versions ne constituent pas encore les pages Services, Réalisations, Tarifs ou Contact. Elles restent dans #15 ; la préversion conserve noindex.

2. Intuition

La décision de langue suit un ordre lisible. On commence par respecter ce qui est déjà explicite, puis on complète ce que l’URL ne précise pas.

1. Préfixe

/en avec un navigateur arabe reste anglais.

2. Choix mémorisé

/ avec NEXT_LOCALE=fr mène à /fr.

3. Navigateur

/ avec ar-MA,fr;q=0.8 mène à /ar.

4. Secours

/ avec une langue non prise en charge mène à /en.

Un cas testé a motivé une normalisation avant next-intl : son algorithme de correspondance approchée pouvait choisir le français exact avant une variante arabe régionale pourtant prioritaire. Negotiator ordonne les préférences et exclut les langues de poids nul ; le proxy retient ensuite la première langue de base supportée. Le cookie et le préfixe gardent leur priorité.

Le sélecteur utilise de vrais liens. Par exemple, depuis /fr?tag=a&tag=b#details, le passage à l’arabe conserve les deux paramètres tag et le fragment details. Le fragment n’est pas envoyé au serveur : cette conservation complète et la mise à jour des liens interviennent après hydratation. Sans JavaScript, les liens restent utilisables vers les routes équivalentes, sans garantie de conservation du fragment.

Le choix manuel est écrit dans un cookie valable un an, même si la langue choisie correspond déjà au navigateur. Cela évite de perdre ce choix lorsque la langue du navigateur change ensuite.

3. Parcours du code

components/language-switcher.tsxPetit composant client : liens accessibles, langue actuelle, paramètres/fragments et préférence explicite.
i18n/navigation.ts, paths.tsPrimitives pour liens localisés et conservation de la route. Les slugs restent partagés dans ce lot.

Preuve de rendu et de comportement

Le build identifie /en, /ar, /fr et /es comme SSG. Les tests HTTP récupèrent le HTML sans exécuter de JavaScript et vérifient texte, métadonnées, lang, direction et liens. Les pages d’erreur sont traitées à la demande ; leur statut HTTP est contrôlé séparément.

pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm start --port 3155
pnpm test:http

Les six scénarios unitaires couvrent clés non vides et parité, négociation régionale, préférence stockée, préfixe prioritaire, conservation des URL et absence de boucle. Trois scénarios HTTP couvrent la matrice quatre langues, la racine et les 404. La CI lance un serveur de production isolé après le build pour ces trois derniers scénarios.

Un contrôle navigateur a également confirmé le passage français → arabe avec les paramètres répétés et le fragment conservés, l’affichage RTL et le retour de la racine vers l’arabe choisi.

Les limites à préserver dans la suite

  • #15 construit les pages finales et fournit leurs vrais contenus traduits.
  • #13 ajoute les formulaires et validations métier ; aucune interface de paiement n’est ajoutée ici.
  • #14 localise les emails et conserve la langue lors d’une livraison différée.
  • #17 traite domaine canonique, métadonnées de lancement, sitemap et redirections historiques. Aucun domaine de production n’est inventé dans ce lot.
  • Les slugs traduits restent une décision explicite avant publication de nouvelles pages.

Cette PR ne déploie rien, n’active aucun fournisseur et ne remplace pas l’application commerciale en production. Ses tests réussis portent sur le socle localisé actuel.
